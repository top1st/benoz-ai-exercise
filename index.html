Part 1 — Handover review

Read against review/handover-architecture.md. Severity: critical = data loss, leak, or legal exposure. serious = breaks under real load or real use.

1. Tenant context leaks across pooled connections

Handover: §1, setTenantContext — SET app.current_tenant = '${tenantId}' with no LOCAL.

Problem: SET (session) survives the request. The connection goes back to the pool still tagged as yesterday’s tenant.

In practice: Request for Client A, then the next checkout of that connection is Client C. RLS reads app.current_tenant and returns A’s rows to C — or C’s rows to A. An unset GUC is fail-closed (current_setting(..., true) is NULL, the policy matches nothing). A stale GUC is fail-open to the wrong tenant. Handlers do not filter by tenant_id themselves; RLS is the only barrier.

Severity: critical.

Fix: SELECT set_config('app.current_tenant', $1, true) inside the request transaction so it is LOCAL and parameterised. Reset or discard the connection if the transaction does not run.

2. Tenant id interpolated into SQL

Handover: §1, same setTenantContext snippet.

Problem: The tenant UUID is concatenated into the query string.

In practice: A crafted tenant id (or a bug that puts untrusted input in that slot) is SQL injection at the isolation boundary. Even without malice, quoting mistakes break or bypass the GUC.

Severity: critical.

Fix: The same set_config($1) call as above. Never build SET with string interpolation.

3. audit_log has no tenant and no RLS

Handover: §1, audit_log table. §7 lists it next to tenant tables but the schema has no tenant_id.

Problem: Writes go to a global log. payload jsonb can hold whatever logAction dumps. The contractor says it is “operational, not tenant-facing” so they skipped isolation.

In practice: Client C is under Israeli privacy law and expects an audit. National ID and clinical notes in payload sit outside RLS. Any app_user session that can read audit_log sees every tenant. You cannot produce a clinic-only audit export. You cannot prove to a regulator that clinic data never left clinic control if the log is in the shared pool.

Severity: critical (legal).

Fix: Add tenant_id, enable RLS with the same policy as the other tenant tables, stop putting clinical fields in payload (or encrypt/redact). Do not treat the log as a debugging convenience.

4. Notification runs inline on create

Handover: §4 createReport — await sendConfirmationSms before the 201. The author is proud that the caller “knows the notification went out.” §6 is the outbox for work that must not block the request.

Problem: Create path contradicts the outbox the same person built. A slow or failing SMS/email holds the HTTP request. A crash after insert and before send loses the notification with no retry.

In practice: Client A’s storm afternoon is 4,000 reports. Each waits on an SMS provider. Timeouts become 500s after the row exists. Client C’s “on Scheduled, email the physician” has the same shape if copied. The 201 is a lie if send fails after insert.

Severity: serious.

Fix: Same pattern as §6: insert and enqueue in one transaction; let the relay send. The 201 means “accepted,” not “the carrier acknowledged.”

5. List handler interpolates the table and selects every column

Handover: §5 listRecords — SELECT * FROM ${table}.

Problem: Table name is interpolated. SELECT * returns every column, including Client C clinical_notes.

In practice: If table is ever request-influenced, this is SQL injection. Even if it is an internal parameter, SELECT * ignores the brief: reception may see name, phone, appointment — not clinical notes. The same handler serves all three clients, so clinic rows leak notes to any role that can list.

Severity: serious, critical if table is not a fixed allow-list.

Fix: Allow-list table names in code. Select an explicit column list (or a per-role projection). Do not return clinical_notes on a reception list.

6. Offset pagination on a non-unique created_at

Handover: §5 — ORDER BY created_at DESC OFFSET $1 LIMIT $2. “created_at has a plain index.” limit comes from the query string.

Problem: Offset over a non-unique sort duplicates and skips rows when inserts land during paging. Deep offsets get expensive. limit is unvalidated. The index is global, not (tenant_id, created_at).

In practice: Call-centre operators page the storm queue and see the same report twice or miss one. At 300 tenants the index does not match the RLS predicate well. A client can pass limit=1000000.

Severity: serious.

Fix: Keyset pagination ((created_at, id)). Cap limit. Index (tenant_id, created_at DESC, id DESC).

7. Outbox idempotency key drops real events

Handover: §6 — handlers “key off an (event_type, entity_id) pair to skip anything they've already processed.” The author is “fairly happy with” this section.

Problem: application.status_changed (and the same shape for reports/referrals) fires more than once per entity. Deduping on entity id treats the second real transition as a duplicate.

In practice: Submitted → Eligibility → … → Approved should send the decision email and later the fourteen-day follow-up. The second status_changed is skipped. Client C’s Scheduled email never goes out if Received already published the same pair. Retries of a true duplicate still need a key — but that key has to include the transition (event id, or (event_type, entity_id, status) / outbox row id), not the entity alone.

Severity: serious.

Fix: Idempotency on the outbox row id (or event id), not (event_type, entity_id).

Things that look wrong but are not

Each item below is something a reviewer could flag; I would not.

A. Transactional outbox (handover §6). Looks wrong: extra table, a polling relay, retries, a dead-letter table — more moving parts than await sendEmail on the request path. Why it is fine: the write and the enqueue share one database transaction. The relay marks a row dispatched only after the broker acknowledges. A crash between COMMIT and publish loses nothing. Retries are capped (five, then DLQ). The defect in §6 is the consumer idempotency key, not the outbox. §4’s inline SMS is the absence of this pattern, not a reason to distrust the pattern where it exists.

B. current_setting(..., true) (handover §1). Looks wrong: swallowing a missing GUC looks like failing open. Why it is fine: missing key → NULL. NULL::uuid does not equal any tenant_id, so the policy matches no rows. Unset is fail-closed. The leak is a stale session SET. Do not “fix” the true flag; fix how the GUC is scoped (set_config(..., true) / LOCAL).

C. custom_fields JSONB + field_definitions (handover §3 / §7). Looks wrong: JSONB looks like EAV. Why it is fine: the product problem is constant “one more field” requests per tenant. Metadata lives in field_definitions; the JSONB column is the payload, not the schema. I would not replace it with per-client tables for custom fields.

D. app_admin bypasses RLS (handover §1). Looks wrong: a role that ignores tenant policies. Why it is fine: migrations and one-off data fixes, not request-serving code. Table owners bypass RLS unless FORCE ROW LEVEL SECURITY is on, so app_user must not own the tables (or FORCE on). That is a hygiene check, not a finding that the admin role is the wrong design.

What I would fix first

I would fix the stale tenant GUC on pooled connections first (handover §1, setTenantContext). It is already live on every request. An unset GUC is fail-closed; a leftover SET from the previous checkout is fail-open to the wrong tenant. Handlers do not filter by tenant_id, so RLS is the only isolation. The change is one call: SELECT set_config('app.current_tenant', $1, true) inside the request transaction — which also removes the string-built tenant id in the same three-line function. I would not start with audit_log (real legal exposure, but it does not swap Client C’s rows into Client A’s UI) or with inline SMS / pagination (they hurt under load; they do not leak another tenant). Until the GUC is trustworthy, the rest of the isolation story is decorative.

Part 2 — Library

Code: https://github.com/top1st/benoz-ai-exercise (public).

validateRecord(definition, record) still returns { valid, errors } with errors as [{ field, message }, ...]. Cross-field checks are a rules array on the definition. The README is the spec: operands are { "field": "name" } or { "value": literal }; operators eq neq gt gte lt lte; six decisions (error target, skip vs loud fail, non-goals). A definition with no rules key behaves as the original library.

Part 3 — Three decisions

Decision 1 — Isolation

The platform is a pool: one database, one schema, tenant_id plus RLS. That is what is already built. I would keep it, and I would not add a silo path.

Client C’s regulator wants clinic data on infrastructure the clinic controls. A shared Postgres, however carefully keyed, is not that. RLS is a software boundary on a machine we operate. It cannot be the clinic’s own control. So I would lose Client C — the private specialist clinic — and any later client with the same regulatory demand. I would tell them so rather than pretend a GUC is a tenancy model their auditor will accept.

What that buys: Client A’s cost and same-day setup stay possible. A new city is a tenant row and a definition, not a database to provision. The unknown fourth client can still land if they look like A or B. The company thesis holds: client differences are configuration, not a second product.

What I am giving up is physical isolation, and with it every regulated tenant who needs it. The fourth client might be another clinic. If they are, we decline them. That is the cost of one approach.

I would still fix the stale-tenant GUC from Part 1. That is not a second isolation model. It is making the pool we chose actually isolate. It does not make Client C legal.

Decision 2 — The eligibility score

The formula lives as versioned tenant configuration, evaluated by a generic scorer. It does not live in application code, and it is not a Client B module. A formula document names the inputs (registry turnover, requested/turnover ratio, five-year grant history with recency weights, that round’s thematic weights), the combination, and the auto-reject threshold. A funding round pins a formula version.

When the board revises the formula (~once a year) or the round’s weights and threshold, we publish a new version. Applications already scored keep the version they were judged under. Re-scoring an in-flight application is an explicit action, not a silent rewrite of last quarter’s auto-rejects.

At score time we snapshot the inputs with the result: the registry API turnover (and the other inputs), the formula version id, the computed score, and the threshold used. The national registry will change. If we only store a number, an audit cannot reproduce why that application was rejected.

When Client C asks for something similar but different, they get the same engine and a different definition — for example a triage/priority formula over wait time and service line — not a clinic fork. Decision 1 still stands: we are not hosting that clinic. The same request will come from the next foundation, or from a city that wants a severity score. One mechanism, many definitions.

Decision 3 — What breaks first

At 300 clients the first component to fail is the global outbox table and its single polling relay (handover §6).

There is one unpublished queue and one process that drains it. Every tenant’s background work — Client A’s SMS, Client B’s decision email and fourteen-day follow-up — is a row in that table. At three clients the relay keeps up. At 300, a Client A storm (4,000 reports in an afternoon) dumps thousands of events into the same place. The relay is one serialization point. Client B’s mail waits behind A’s backlog.

What I would see: outbox depth climbing and not returning to baseline; time from COMMIT to broker ack stretching into minutes, then hours; dead-letter growth as handlers exhaust retries on work that is already stale; operators reporting that the status changed but the email never went.

What I would do: partition the outbox and the relay by tenant so A’s storm cannot starve B. Per-tenant queues, or a poll that fair-shares by tenant_id, are the same idea. That is the change for this component.
